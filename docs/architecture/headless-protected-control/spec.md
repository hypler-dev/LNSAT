# Specification: HCFG-5A protected online configuration transitions

Status: proposed
Intent: [HCFG-5A intent](intent.md)
Owner: LNSAT maintainers
Last updated: 2026-09-27

## Behavior

HCFG-5A defines an online `config apply` transition for an installation that has already completed a separately authorized local bootstrap. A versioned Gateway request and `lnsatctl` client may replace the active headless declaration only when the caller, prior generation, exact candidate, resource identities, current policy, and any human decision are verified. The transition is one durable atomic authority event. Applying a declaration does not authorize an action: each later admission still intersects the active generation with Gateway policy, approval obligations, resource and runtime restrictions, and persisted stop/revocation state.

The HCFG-3 declaration is a ceiling, not an owner grant. Its `installation_ref` and resource identity digests are untrusted input until the Gateway binds them to the bootstrapped installation and platform-verified canonical resource identities. CLI source-file identity checks protect a bounded read; they do not establish ownership or substitute for resource identity proof. The daemon reparses and recomposes the exact submitted bytes independently of the CLI diagnostic result.

### Transition classes

| Candidate relative to current effective authority                                                                         | Decision                                                                                                            |
| ------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| Exact semantic equality and same resource identities                                                                      | Authenticated owner may record an idempotent no-op; no new active generation.                                       |
| Strictly narrower resource reachability, action modes, or budgets, with no identity substitution                          | Authenticated owner may apply after current validation.                                                             |
| Any new resource, principal/action grant, weaker approval, larger budget, changed resource identity, or incomparable rule | Privilege increase; require a fresh authenticated owner decision bound to the exact candidate and prior generation. |
| Candidate cannot be compared, identity/enforcement proof is missing, or an active stop/revocation would be weakened       | Deny. No new authority.                                                                                             |

The comparison uses the currently active **effective** envelope and persisted revocation floor, not just two declaration JSON files. It preserves the HCFG-3 compiled capability floor and layering rules. Unknown capabilities, unsupported platform controls, and unverified target identity fail closed. A candidate cannot reduce a `deny` or approval obligation by changing a reference or presentation layer. Removal of a resource is narrowing only if it cannot move an existing rule to a different identity.

`lnsat.headless_config.comparison.v1` is the proposed deterministic comparison. Its input snapshot binds installation ID, old generation ID/digest, old and candidate canonical declaration digests, the same current policy/floor version for both sides, persisted stop/revocation epoch, and verified identity-evidence digest for every resource on either side. If either side cannot be rederived under that one snapshot, comparison returns `unverifiable` and apply denies. The snapshot and comparator version are hashed as canonical JSON using the HCFG-3 canonical writer; the resulting digest, not display prose, is the approval binding. Gateway recomputes the snapshot and digest under the apply transaction and rejects any change.

For each sorted `(principal_ref, resource_ref, capability)` tuple in the union of both composed envelopes, an absent rule is `deny`. Access order is `deny < approval_required < allow`; a rule is narrower only when its mode does not rise and each of the five HCFG-3 budget limits is no greater than before. Denial has all-zero limits. Candidate resource membership must be a subset for narrowing, and each retained resource must have the same verified canonical identity; adding or substituting an identity is widening even if its displayed reference is unchanged. A tuple with both a narrower and a wider dimension is `mixed` and requires the widening decision. The overall result is `equal` only if all dimensions and identities match, `narrowing` only if every dimension is no greater and at least one is lower, and `widening_or_mixed` otherwise. Unsupported capability, noncanonical tuple, missing identity evidence, changed policy/floor snapshot, or incomparable platform evidence is `unverifiable`, never an approvable widening. The sorted change tuples, old/new digests, and result form the canonical comparison summary committed by its digest; the redacted UI summary is never the authority.

### Authorization and human decision

Candidate preparation and final apply both require an active owner session, independent proof, exact Gateway route authorization, and a session-bound request. Operators and agents have no V1 configuration-prepare or decision permission. A browser/UI client and `lnsatctl` receive no direct store or OS-mutation path. The owner may apply a strict narrowing without a separate step-up decision. A privilege increase has two durable steps: prepare an inert candidate and record a fresh authenticated owner decision on its exact comparison. A single owner may perform both steps; the second step must require current owner credential reauthentication, independent session proof, and explicit confirmation of the exact canonical comparison digest. A session token, request capability, generic approval, automated client flag, or mere repetition of the prepare call cannot produce the decision. A stopped installation is not implicitly resumed by apply.

The Gateway issues a random, one-use, time-bounded owner-decision challenge only after rederiving the inert candidate and `comparison.v1`. The durable challenge binds installation ID, requester identity/session, current owner credential generation, current active generation ID and digest, candidate canonical digest, comparison snapshot and summary digests, trusted expiry, and challenge nonce. The protected decision view shows the authenticated owner enough exact resource/action/identity changes to judge the increase, while excluding secret values and raw credentials. `lnsatctl` requires an interactive confirmation and fresh owner-credential input for widening. It accepts that credential only from a masked controlling-terminal prompt, never a command argument, environment variable, standard input, flag, or auto-confirm option. If no controlling terminal is available, widening fails. The server authenticates the credential itself; only the existing authenticated local request may carry it transiently. Raw credential bytes never enter persisted request, candidate, decision, audit, log, telemetry, or readback. Neither a terminal prompt nor credential proof claims to prove biological human presence. API clients may prepare a candidate, but cannot assert that a human approved it. A later UI must use the same protected Gateway decision step.

Decision creation uses one immediate transaction: re-read the challenge, current owner/session/credential generation, exact candidate and comparison bindings; authenticate the freshly supplied credential; consume the unused challenge exactly once; and append a separate one-use configuration owner-decision record containing the authenticated credential-generation reference/digest. A mismatch or concurrent duplicate rolls back the whole decision. At apply, Gateway rederives the candidate and comparison, checks the decision has not expired or been consumed, requires its recorded credential generation to equal the current owner credential generation, and checks the current owner identity, session, and challenge bindings under the same authority-store transaction. The requesting and deciding owner may be the same identity only for this configuration-specific step-up. Candidate bytes or CLI assertions cannot choose the transition class or decision requirement. Credential rotation before decision creation or before apply, a stale challenge, changed generation, changed identity evidence, replay, or substitution denies. This does not change the existing distinct-requester/approver rule for consequential action approvals.

An owner decision permits only the exact configuration transition; it does not itself activate a resource, issue an execution authorization, or waive a later action-specific approval. Generic action-approval records cannot be relabeled as configuration decisions. The exact fresh-credential/challenge contract requires separate owner security acceptance before source implementation; absent that decision, widening remains closed. LNSAT can verify credential possession and a recorded explicit confirmation, but cannot prove a biological human was present; owner credential custody and local host control remain the V1 trust assumptions.

## Interfaces and contracts

The proposed versioned API exposes an authenticated candidate inspection/diff read and an authenticated apply mutation. `lnsatctl config diff` may display a redacted semantic comparison, but the Gateway computes it again at apply. `lnsatctl config apply --declaration <absolute-path> --expected-generation <id>` submits bounded declaration bytes and an exact compare-and-swap generation; the command requires explicit product-surface selection and must never infer permission from `config effective` or `config export`. Exact route names, request/response schemas, permission names, and transport headers are frozen only in the later implementation packet after this authority decision; no existing route is changed by this proposal.

The request binds one canonical declaration digest, one expected active generation ID and digest, one installation ID, one idempotency key bound to the full request digest, and, for widening, one exact decision ID. The server derives all other fields. The response is a redacted fixed-schema result: `applied`, `no_change`, or a fixed denial code; on success it includes new generation ID/digest, previous generation ID, audit event ID, and authority epoch. It excludes raw paths, principals, resource details, session headers, proof, declaration bytes, and private decision content. Unknown fields, duplicate fields, oversized input, ambiguous identity, or unsupported version fail before mutation.

Generation IDs are unique durable records. The active pointer and authority epoch belong to the same installation, but SQLite rows alone cannot distinguish a copied or stale restored store. Activation therefore remains blocked until a separately accepted store-anchor contract defines a trusted value outside SQLite and outside ordinary database backup: creation at proven local bootstrap; binding to host, owner, installation, and active generation; update ordering with the SQLite transaction; clone and older-snapshot refusal; stop/revocation persistence; explicit inert restore; recovery after interrupted update or anchor loss; and selected-platform proof. A missing, copied, stale, or unverifiable anchor denies all activation. No source packet may implement active apply by treating an installation ID, digest, or epoch inside SQLite as that anchor. Redacted `config show`, `status`, and audit readback must distinguish a candidate, active generation, stop state, and denial without claiming that an in-flight action was cancelled.

## States and failure handling

The authority store records immutable generation history and one active pointer per installation. Apply proceeds as follows:

1. Authenticate the owner and exact transport. Parse and compose the candidate with the closed HCFG-3 contract. Resolve installation and current generation from trusted store state. Recheck canonical resource identity and selected-platform enforcement capability; HCFG-6 must have proven those controls before activation.
2. Compute semantic comparison and, if needed, verify the fresh owner decision. Prepare external enforcement so the candidate cannot gain authority before commit. If any preparation fails, retain the prior active generation and report a fixed denial; cleanup cannot grant authority.
3. In one immediate SQLite transaction, re-read owner/session, trusted installation, current generation and authority epoch, stop/revocation floor, resource-identity evidence, and decision. Reject a stale expected generation or changed evidence. Insert the immutable new generation, consume the exact decision once, move the active pointer and epoch, append audit/source events, and rederive the committed linkage before commit. Failure rolls back every source and audit write.
4. New admissions read the committed active generation and epoch, then revalidate resource identity and enforcement at use. If the active pointer, stop, revocation, or identity changes before use, admission fails and must be retried from a new authority evaluation. A dispatched action keeps its prior receipt/reconciliation obligations; no apply result proves it did not execute.

The transaction must never perform a partial external permission grant. If the selected OS adapter cannot prepare restrictions without opening authority early, activation for that adapter is unsupported. A crash before commit leaves the prior generation active; a crash after commit is resolved by durable readback and idempotency key, never by client inference. A retry of the same idempotency key and identical request returns its prior committed result; a changed request denies. Concurrent applies have exactly one winning expected generation. Timeout or transport loss returns `unknown` to the client until exact authenticated readback verifies the durable result.

Every authenticated `applied` or `no_change` result has one immutable `configuration_transition.v1` event in the same transaction as its request/idempotency record, decision consumption (if any), generation insert (if any), and active-pointer update (if any). The event binds installation ID, event ID, trusted time, request digest and idempotency-key digest, requester identity/session references, deciding owner identity/challenge/decision references or explicit `none`, `comparison.v1` version/snapshot/summary digests and result, old/new generation IDs and digests, resource identity-evidence digest, policy/floor version, stop/revocation epoch, old/new authority epoch, outcome, and previous event digest. The event digest covers those canonical fields and the previous digest; no event is pruned before a separately accepted retention/export policy preserves verifiability. A true `no_change` has equal old/new generation and epoch, creates no generation, and is still audited once. An exact idempotent replay returns the original event/result without a second event. Unauthenticated denial emits no applicant-specific details; an authenticated denial may append a separate sanitized security event only if it cannot weaken the fail-closed transaction rule. Failure to append the success event aborts activation.

Emergency stop and revocation state outrank every generation. This packet does not define their mutation interfaces; apply must fail while a stop is active and must not clear revocations. Rollback is a new apply request against the current generation, subject to the same comparison, current revocation floor, decision, identity, and enforcement rules. It cannot point the active pointer back to an old row or restore authority revoked since that row was created. Resume and local restore have separate contracts.

## Data, privacy, and permissions

The store must retain the canonical declaration, composed envelope, policy/floor version, verified identity-evidence digest, decision bindings, immutable generation, and audit chain needed to rederive the active ceiling and each transition. Resource/principal references and canonical target identities are sensitive local operational data; they stay in the protected local store and are excluded from logs, generic errors, telemetry, and public diagnostics. Secret values are never accepted as configuration content; only references may appear. Session tokens and independent proofs are never persisted raw. The separate configuration owner-decision record stores bounded binding digests and owner attribution sufficient for audit without credential material. Its schema and permission are distinct from the existing action-approval record and `DecideApproval` permission. Redacted readback is a closed projection, never a generic serializer of stored rows.

Only Gateway has online mutation authority. `lnsatctl` uses the same authenticated versioned interface. MCP, adapters, agents, future UI, and read-only Control Center receive no alternate apply path. Store unavailability, audit failure, stale session, unsupported OS proof, or missing fresh owner decision deny new authority. Existing action-specific approval, nonce, execution-authorization, and receipt rules remain mandatory.

## Compatibility and migration

This is a new pre-1.0 contract proposal. HCFG-3 diagnostic commands and their non-applicable redacted export remain unchanged. Existing `lnsat.daemon.config.v1` is process startup configuration, not an active headless declaration; it must not be silently migrated or interpreted as a resource grant. A later schema migration must initialize no active generation from existing diagnostic input. Existing installations stay non-activated until a separately authorized bootstrap path binds owner, installation, and first configuration. Source rollback may restore code but cannot downgrade or erase a durable authority epoch; explicit recovery must preserve stop/revocation and audit history.

## Acceptance mapping

- Unit/model tests prove semantic comparison in both resource and action dimensions, denial/approval ordering, budget changes, identity substitution, incomparability, compiled floor, and revocation monotonicity.
- Store tests prove compare-and-swap, one-use challenge and decision, parallel decision attempts, credential rotation before and after reauthentication and before apply, duplicate challenge and decision replay, same-transaction source/audit, idempotency, crash/retry readback, copied-store generation invalidation, stale decision, and concurrent apply.
- Gateway/CLI tests prove owner auth plus independent proof, masked controlling-terminal secret input, rejection of credential arguments/environment/standard-input/auto-confirm options, no raw credential in persisted request/audit/log/readback, generic denial, exact versions/fields, redacted output, no direct store bypass, and no authority from diagnostic commands.
- HCFG-6 platform tests prove grant/use identity under symlink/reparse, mount, target replacement, unsupported control, and revocation race on each selected target. Phase 13 repeats interruption and recovery tests. Source conformance alone is not selected-target runtime proof.
- Fresh independent security review checks this exact contract before owner acceptance, then reviews source and evidence before any merge decision.

## Non-goals and open questions

Initial owner/installation/configuration bootstrap and host-owner proof; fresh owner-decision challenge and credential-recheck route; emergency stop/resume; offline backup/inert restore; active generation export/import; HCFG-4 watch; HCFG-6 OS adapters; Docker/runtime proof; package and release remain separate decisions. **This activation specification cannot receive owner acceptance yet.** First accept separate exact records for (1) the bootstrap trust root and one-time owner/installation/first-generation binding, including interruption and forged/substituted/replayed denial; (2) the fresh owner-credential/challenge flow, protected decision view, one-use binding, credential rotation, and agent/client self-approval denials; and (3) the external store-anchor lifecycle listed above, including clone, stale restore, post-revocation rollback, interrupted update, and anchor-loss tests. Until those decisions, the only eligible source proposal is a pure non-activating `comparison.v1` implementation with no store, route, or CLI mutation. No new mutation authority is inferred from this document's presence.
