# UI And Framework

Status: framework expansion proposal. Checked-in `apps/console` already uses
Next.js, React, and TypeScript; current routes and read-only behavior are
documented in
[Control Center information architecture](MANAGEMENT_UI_INFORMATION_ARCHITECTURE.md).
Library and route recommendations below are future options, not shipped scope.

## Recommendation

Use **Next.js App Router + React + TypeScript** for the operator UI, but keep
LNSAT's real security boundary and business logic outside Next.js.

Recommended split:

```text
apps/console        Next.js operator UI
apps/api        Fastify gateway API
packages/core   shared domain contracts
packages/packets packet schemas, validation, canonical hash
packages/policy policy decisions and capability model
packages/audit  audit event contracts
packages/cli    local CLI
packages/mcp    MCP adapter
```

## Why This Split

Next.js is the right UI framework for:

- operator console routes
- nested layouts
- server-rendered documentation/status pages
- client islands for packet inspectors, tables, forms, and graphs
- static, read-only product surfaces

Fastify is the better gateway/API boundary for:

- packet validation
- JSON Schema route contracts
- OpenAPI generation
- adapter-facing APIs
- policy/audit enforcement

Do not make Next.js API routes the LNSAT security boundary. The UI calls the
gateway; the gateway owns identity, packet validation, policy, approval, and audit.

## UI Libraries

Use:

- Tailwind CSS
- shadcn/ui with Radix primitives
- lucide-react icons
- TanStack Query for server state
- TanStack Table for packet/audit/resource tables
- React Flow for node/substrate/fabric graphs
- Monaco Editor later for packet JSON and HPL-Code inspection
- uPlot or ECharts later for dense telemetry charts

## Operator UI Shape

The UI should be a dense operator console, not a marketing dashboard.

Initial routes:

```text
/projects      project onboarding, readiness, source refs
/agents        actor identities, roles, sessions, allowed actions
/packets       compiler, inspector, validation, canonical hash
/policy        capabilities, risk levels, decisions, approvals
/audit         append-only event ledger
/nodes         node telemetry, services, substrates, route/fabric status
/sandboxes     Git/container sandbox runs once built
/settings      install mode, trust boundary, local/SaaS/hybrid posture
```

Expanded downstream routes may add work contexts, profiles, skills,
instructions, graphs, connectors, modules, models, libraries, and organization
administration. Portable contracts and evidence remain public; rich
collaborative implementation may live in `LNSAT-Commercial`.

## Relationship Views

UI needs more than one visual grammar:

- inventory/tree/table for dense infrastructure-style management;
- node graph for delegation, inheritance, context, policy, and connector
  relationships;
- material-editor-style graph for workflows and effective profile composition;
- structured form for common safe settings;
- Monaco or equivalent source/diff editor for exact agent files, instructions,
  manifests, and uncommon rules;
- timeline for versions, assignments, approvals, receipts, incidents, and
  rollback.

Graph edges and nodes are versioned data, not browser-only state. Drag/drop
creates proposal and diff; Gateway controls activation. UI must expose exact
resolved source, origin, digest, compatibility, assignment, approval, and
rollback evidence.

## First UI Boundary

First UI is read-only except packet validation.

Allowed early actions:

- inspect packet fixture
- validate packet
- view canonical hash
- view policy dry-run result
- view audit events generated by validation/dry-run

Blocked until later:

- run command
- deploy
- restart service
- mutate database
- enqueue job
- load model
- execute runbook
- change secrets
- change DNS/cloud resources

## Visual Direction

Use restrained operational design:

- dense but readable tables
- small status chips
- source-backed detail drawers
- split-pane packet inspector
- graph view only where relationships matter
- entry-level safe presets plus progressively disclosed granular controls
- quiet color system with risk/status accents
- no marketing hero layout inside operator app
- no decorative background effects in work surfaces

## First Web App Milestone

Do not expand UI into mutation before the relevant packet, Gateway, policy,
approval, audit, and rollback evidence exists.

First UI milestone already exists as a read-only Packet Inspector-style surface.
Future UI work should stay inspection-first unless an active packet explicitly
opens mutation scope.

```text
Packet Inspector
  -> paste/load fixture
  -> validate
  -> show canonical JSON
  -> show stable hash
  -> show policy dry-run
  -> append audit event
```

Next UI-eligible surfaces should be evidence viewers for current platform
primitives, such as substrate control intent, capability broker request, and
future adapter manifest inspection. Do not build live broker dispatch, adapter
invocation, deploy, service restart, database mutation, queue mutation, SSH,
Docker runner, node-agent, Git mutation, DNS/Cloudflare mutation, or secret
handling into UI without explicit later packets.

Every browser capability needs an equivalent versioned API and, where
operationally useful, OS CLI path. UI cannot become only route to recovery,
automation, evidence export, or configuration inspection.
