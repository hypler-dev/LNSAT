# Specification: HCFG-6 observed resource and runtime enforcement

Status: accepted
Intent: [HCFG-6 intent](intent.md)
Owner: LNSAT maintainers
Accepted by: human owner on 2026-10-01 at exact PR #72 head `0dbe0a2874428721b1a4ba6bad1708ec5fdbb572`; see Project Status
Last updated: 2026-10-01

## Behavior

HCFG-6 must verify declared resources at grant and actual use. Verification never authorizes an action. Gateway still checks identity, policy, distinct approval when required, exact one-time authorization, installation/generation/epoch, stop/revocation state and audit. The final outcome includes nonempty target enforcement; zero resources and source fixtures alone cannot satisfy it.

### First concrete capability tuple

The accepted initial engineering backend is one same-host Linux Docker Engine execution cell with an identity-mapped nonzero workload UID/GID, an explicitly selected trusted local daemon, one marked disposable Git repository and one exact Docker runtime profile. This is an engineering capability proposal, not an OS/architecture package support row. LNSAT itself remains non-root. A privileged Docker daemon is an explicitly trusted host component; its access must be restricted to the trusted owner/administrators and the private supervisor, never agents or the adapter.

| HCFG resource kind                              | Initial verifier and effect                                                                                                                                                                                                                                                                    |
| ----------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `repository`                                    | Exactly one explicit marked disposable Git target. Held canonical directory identity, marker/Git identity and per-action semantic target digest; exactly one writable nonrecursive bind at the profile target.                                                                                 |
| `runtime_profile`                               | Exactly one explicit stable regular profile file. Canonical profile/authority digest, image config ImageID plus separately verified manifest/index association, adapter/Docker/verifier identities and selected control recipe. No target mount or action permission follows from this record. |
| `folder`, `service`, `connector`, `os_resource` | Unsupported in this backend. Reject a declaration containing one, including a resource narrowed away later. Never omit it or treat a digest as verification. Future versioned verifier packets may add these without changing authority semantics.                                             |

The owner must select a nonempty repository plus its runtime profile. Allowed action rules are still constrained by the compiled Git capability floor and approval requirements; declaration and binding cannot add an action. No arbitrary repository, read-write folder, service, extra mount, host device or shell is silently substituted. A typed empty/unsupported result remains denied, not a successful installation.

### Exact initial backend

The only accepted positive engineering backend is Docker Engine **29.8.2**, rootful daemon on the same Linux host, pinned Engine API **1.56**, cgroup v2 with systemd-managed CPU/memory/PIDs controllers, Docker’s bundled containerd **2.3.6** and runc **1.5.2**, default seccomp and default AppArmor enabled. This is a dated engineering recipe, not an installed-host observation or support promise. Alternate engines/generic OCI, rootless/userns remapping, Docker Desktop, remote daemons, other API/implementation versions, disabled/modified default security profiles and unavailable controllers deny. The controller and adapter run with the same explicitly selected nonzero host-mapped UID/GID; supplementary groups are empty. No automatic API negotiation, privileged LNSAT helper or alternate backend fallback is allowed.

The endpoint is the single explicitly selected absolute Unix socket in the new schema-3 profile. Its private physical path is supplied by a future owner-selected run manifest, never discovered or committed here. Require stable named/opened endpoint identity, root peer UID from `SO_PEERCRED`, root-controlled non-writable path ancestry, and kernel-observed socket access restricted to root/trusted administrators and the exact nonzero controller UID. Unverifiable ACL/group membership or a proxy with another peer identity denies. An effective ACL may permit this exact controller; the installer never creates or relaxes that ACL automatically. The rootful daemon, root administrator and kernel are explicitly trusted host components; agents and container processes have no such socket permission.

Use bounded private HTTP/1.1 over that pinned socket, with all paths prefixed `/v1.56`. Permit only `GET /version`, `GET /info`, `GET /images/{exact_config_image_id}/json`, own-object `POST /containers/create`, `POST /containers/{id}/attach`, `POST /containers/{id}/start`, `GET /containers/{id}/json`, `POST /containers/{id}/wait`, `POST /containers/{id}/kill`, and `DELETE /containers/{id}`. The one deterministic preparation name below is allowed for exact orphan inspection only. All IDs come from privately checked current create/inspect results tied to the preparation/attempt; arbitrary names, paths, filters and URLs are denied. No pull, build, exec, prune, registry authentication, global enumeration, volume or network mutation endpoint is available. Attach is established before start with TTY disabled and explicit stdin/stdout/stderr flags; bound and validate Docker’s stream framing separately from the startup protocol. Reject redirects, unexpected content/framing, extra objects, unsupported status, ambiguous response and deadline/byte excess.

Authenticate the default seccomp/AppArmor recipe through a root-provisioned, stable read-only implementation manifest binding exact Engine/containerd/runc artifact bytes, build identities and the security-template recipe for Engine 29.8.2. Verify its artifact/provenance and current private daemon identity, inspect the effective security selections and derive native mode/privilege observations. A version string or caller manifest is insufficient, and kernel `Seccomp:2` does not reveal a filter digest. The actual component/template digests and host kernel recipe remain `UNSET_BLOCKING` until the separately reviewed source/run freeze; no source activation or proof can occur while they are unset. Selected-target syscall/namespace/mount/limit negative behavior is still mandatory. Future security updates require a reviewed recipe change, not silently widening this pin.

### Explicit owner binding and host observation

Use one explicitly supplied absolute owner-controlled `lnsat.resource_bindings.v1` file alongside the unchanged HCFG-3 declaration. It contains exact `schema_id`, `contract_version: lnsat.contracts.v1_0`, `installation_ref`, and sorted unique `bindings`. Each binding contains only `resource_ref`, `kind`, and absolute canonical `source_path`. No environment expansion, secret value, endpoint discovery, fallback, executable selection, policy or grant is accepted. Maximum 64 KiB UTF-8, 128 rows and 4,096 bytes per path; reject duplicate/unknown fields, trailing data, malformed references and nulls.

Both files use the bounded stable explicit-file loader. Require nonzero equal real/effective owner UID, regular single-link owner-only file, owner-only parent, no symlink components, stable opened/named identity, and unsupported effective ACL proof denial. The binding dictionary must exactly match every HCFG-3 resource reference/kind. Every asserted identity digest must match independently observed identity before initialization or configuration apply. A mismatch denies; the verifier never rewrites the declaration to make it pass. Only an explicit owner operation may replace bindings and obtain a newly approved generation.

For repository observation, retain a private metadata-only canonical root handle and validate the path component chain, type, owner/access, device/inode and mount identity. Never follow symlink/reparse components or cross an unapproved mount. Reject submounts and external hard links; bound the tree metadata walk to 100,000 entries and 16 MiB total path bytes and deny incomplete scans. Reuse the existing marker, repository-root and closed Git-target checks, retaining their disposable-only scope. Reject alternate Git object/worktree directories and configuration that escapes the target. Owner-only containment prevents an untrusted host user from replacing the root; current handle/path/marker/mount checks detect drift. Trusted host-owner manipulation remains outside anti-tamper claims.

Identity bytes are private. Hash compact UTF-8 JSON arrays under domain `lnsat.hcfg_resource_identity.v1` followed by LF: repository tuple `["repository", canonical_path, device, inode, host_owner_uid, marker_digest]`; runtime tuple `["runtime_profile", canonical_path, device, inode, host_owner_uid, profile_digest, authority_digest]`. Use unsigned decimal integers, lowercase prefixed SHA256 strings and exact string escaping, with no optional tuple entries. No timestamps that normal approved repository writes change are identity fields. An open handle prevents same-live-object inode reuse; restarted observation must revalidate the stored tuple and current target. This is local identity under the trusted host-owner model, not immutable filesystem content or independent freshness.

Mount IDs and namespace IDs are live comparison tokens, not persistent resource identity. Linux mount IDs can be reused after unmount, and a bind in another mount namespace has its own observation. Correlate each held resource directory with its current kernel mount record; compare host and adapter device/inode and the approved mount policy, never require equal host/container mount IDs. Hold the directory while comparing bounded descriptor metadata and mount records before and after use; changed, missing, inconsistent or unsupported association denies. Restart must rederive current mount/namespace evidence and verify the approved policy rather than treating an old numeric token as freshness. The proposed resource observation may read bounded genuine `/proc/self/fdinfo/{held_resource_fd}` metadata; it must not reopen a resource through `/proc/self/fd` or add a selected-store database alias. Procfs origin, descriptor lifetime, parser bounds and the safe native API remain part of the required source freeze.

### Bootstrap preparation without target action

The human owner accepted the amendment to HCFG-5B specification’s “without opening a resource” precommit rule on 2026-10-01 at exact PR #72 head `0dbe0a2874428721b1a4ba6bad1708ec5fdbb572`. The reconciled exception permits only the bounded host-side identity observations defined here: metadata-only directory descriptors and bounded marker/Git identity reads; it permits no target-mounted workload or action authority. Before bootstrap commit, marker/Git identity reads are bounded host-side metadata reads only; no Git subprocess, content modification or target action is permitted. Per-action semantic Git verification remains a later held-identity use check. Current source remains unchanged and must not enable this sequence before the reviewed source freeze and integration gates are satisfied. Bootstrap starts no target-mounted workload. Its separately authorized zero-authority platform probe uses the exact immutable probe/adapter image with no resource binding, no action frame, no socket/device/credential mount, fixed image environment and the restrictive control recipe. It observes selected daemon/kernel/cgroup/security capability and behavior, then proves bounded removal. Preparing an inert owner-only binding/recipe record creates no permission grant.

Such preparation is outside SQLite and under the daemon-shared lease. It must be idempotent by the precommit preparation identity defined below, have a durable owner-only bounded preparation journal, detect incomplete/orphaned prior preparations, and never infer success from a label or missing response. Unknown cleanup quarantines initialization/admission until explicit offline host-owner inspection proves exact object removal. No host ACL, mode, owner, mount, namespace or daemon setting is automatically changed to pass a probe. No process or OS mutation occurs inside the later immediate bootstrap transaction.

Preparation has its own fixed, finite administrative probe budget, frozen and reviewed with the immutable recipe before implementation. Its CPU, memory, task, wall-clock and output bounds may be stricter than the runtime profile but never exceed it. This is distinct from an agent action budget: HCFG-3's absent or denied rules deliberately produce zero action limits, while a valid runtime profile has positive process ceilings. A deny-all declaration must therefore permit only this separately accepted owner preparation, without converting its zero limits to an allow rule. No target mount, action frame or reusable authorization results. Probe overrun or a profile too small for the fixed recipe denies preparation; never borrow an action budget, silently enlarge a ceiling or default to unlimited. Per-attempt startup and action instead share the single most restrictive composed/profile/action budget; startup time and output count toward it, with no reset at release.

The accepted atomic bootstrap repeats store, declaration, binding, resource identity and current preparation checks inside its own transaction; it persists the complete owner/install/generation/binding/audit together. The prepared recipe proves available restrictions without granting target access. Actual target-mounted OS enforcement is proved again for every action before release. A cached probe or persisted digest is never sufficient at use. Source-only preparation diagnostics cannot initialize or admit a store.

### Preparation order, journal and crash custody

Under the held selected-store lease, load/validate the explicit declaration and binding before observing resources. Resolve bounded metadata using private close-on-exec directory handles; no descriptor is sent to Docker/adapter or serialized. Hold the verified roots and their permitted ancestor identities through preparation and all immediate-transaction rechecks, then close on every success, denial and exception. A crash lets the kernel close them; a later process must reopen and rederive current identity, never restore a numeric descriptor. Persist no raw resource path, tree entry, UID mapping, descriptor number or native proof in the journal/public audit; private source paths remain only in the owner’s binding file. The journal carries fixed opaque digests and the numeric owner UID needed for custody, not resource contents.

Before any resource-free probe creation, allocate `preparation_id` as 32 random bytes encoded in 64 lowercase hex digits. There is **no installation ID yet**. Derive `candidate_digest` from canonical declaration/composed/binding digests, selected-store binding digest, owner UID and the frozen profile/recipe digest under `lnsat.hcfg_preparation_candidate.v1` plus LF. Create a no-clobber single-link 0600 bounded 16 KiB journal in an exact owner 0700 private preparation directory under the selected-store parent, reject ambiguous ACLs/symlinks/other-owner state and fsync file/directory. Record preparation ID, candidate/store/recipe digests, owner UID, challenge digest, phase, deterministic name `lnsat-hcfg6-probe-{preparation_id}`, and at most one exact returned container ID. The name/challenge are fixed before the create request; no label-only cleanup or global search is permitted.

Journal phases are `pending`, `probe_created`, `cleanup_verified`, `bound` or `quarantined`. A label/name alone never proves ownership or safe removal: privately inspect the exact named/ID object and compare its image, complete zero-resource create recipe, challenge, owner/candidate labels and current daemon identity. On a lost create response, only that exact name may be inspected; conflicting/incomplete identity quarantines without deleting it. Prove owned-object removal under the same private endpoint before marking `cleanup_verified`. Detect all prior nonterminal journal entries under the lease before new preparation; unknown entries, unproved absence/removal or ambiguous durability quarantine. Never reuse a preparation ID or interpret an old journal as a permit.

After successful cleanup, the accepted atomic initialization may create its random installation ID and bind the exact preparation ID/candidate/recipe/journal digest into the single bootstrap transaction’s installation/configuration audit alongside all owner/generation/binding rows. The journal is not an independent trust root. After commit, set `bound` only after exact current local store/audit readback. A crash before that journal update resolves through the complete SQLite binding: fully committed means readback, never reinitialize; no matching committed binding means prove cleanup, retain terminal evidence and require a new random preparation ID. An ambiguous/partial committed binding denies. No process creation, cleanup or permission change occurs inside the SQLite transaction. The accepted bootstrap artifacts reconcile this ordering and metadata exception with the owner decision recorded in Project Status. The exact source freeze and its independent review still precede implementation.

### Per-attempt observed startup barrier

This requires a new explicitly selected Docker profile schema 3 and `lnsat.adapter_process.docker_local.v2` startup protocol. The existing schema 1/2 profile, D3/D4A frames, current launch digest and locked Phase 11 driver remain unchanged. There is no fallback, automatic upgrade, or mixed-version activation. Exact new wire frames/canonical encoding and profile-to-generation authority digest must be frozen and reviewed before behavioral source integration.

1. Before process creation, the private store guard rechecks the complete active bootstrap binding, generation/epoch, approved resource/profile/action digests, stop/revocation and exact durable claim/attempt. Consume the original bounded attempt once. Never create a replacement attempt to retry verification.
2. Revalidate the selected executable, connected Unix endpoint/peer and owner-controlled resource handles. The observer accepts only its own private pinned same-host connection/attach channel; no public trait, callback, imported inspect document or serialized permit can satisfy it. Socket metadata alone is insufficient. Explicitly deny unsupported daemon identity, remapping, endpoint access control or API behavior.
3. Create/start only the exact immutable trusted adapter in its inert startup state. Pass no action payload, bearer, session proof, infrastructure credential or authorization frame. Bind a fresh random challenge to installation, generation/epoch, operation/attempt, candidate/profile and exact container ID. Until release, the adapter can only produce bounded native observations and wait; it must not perform a Git operation, run a shell or spawn target tooling. The attempt is already durably consumed, and post-create interruption is not proved non-execution merely because stdin was withheld.
4. Compare two independent local evidence classes: private trusted-daemon inspect/configuration and the pinned adapter's bounded kernel-derived startup response over the exact attach channel. Inspect gives exact container/image/config, one bind source/destination and selected recipe; the kernel response gives actual mounted-root device/inode, namespace/mount/cgroup identity, effective UID/GID, capability sets, `NoNewPrivs`, seccomp mode and actual root/resource mount flags. Only the immutable adapter derives these from its live process; caller-authored fields are never accepted as current state. Check the adapter/probe artifact identity and the source of every required field. Mode 2 seccomp alone is not proof of a particular filter, and a JSON mount source alone is not inode proof.
5. Require the complete recipe below. Reobserve the host handle/path/marker and runtime identity. Re-read active generation/epoch/stop/revocation and claim under one fresh authoritative store transaction immediately before releasing the exact action frame. Consume a private one-use startup guard bound to this same live container/attach channel. It has no wire serializer, `Clone`, `Debug`, caller constructor or conversion from diagnostic evidence. Require one private installation-wide release/revocation serialization boundary, also respected by all generation/stop/revocation writers and backed by the exclusive daemon lease. Under it, an immediate transaction checks current state and commits a one-use release-intent audit binding this attempt/channel/epoch. Keep serialization held through the bounded exact frame write; no stop/revocation commit may interleave. The transaction commit is the grant linearization point, not evidence of execution. A revocation committed before it denies; a revocation after it cannot assert an already granted action never happened. Write/commit ambiguity remains consumed/unknown and never resends the frame. Source integration must prove every writer participates and the write deadline bounds the lock.
6. After release, retain current bounded consequence verification, receipt or `outcome_unknown`, restart/reconciliation and cleanup obligations. Any endpoint/container/resource/control drift, transport loss, unexpected output or unproved cleanup after create preserves the consumed attempt and denies release or further work. No redispatch occurs. A stop/revocation denies subsequent release/new admission; an already released action may have happened and must retain evidence/unknown semantics.

The startup process intentionally opens the selected mount to observe its identity only after the original action attempt is claimed. It is trusted versioned adapter code, not an agent process. This proposed staging does not claim OS isolation from malicious code inside that trusted adapter, nor biological owner presence. The OS restrictions bound the later action workload's reachability; authorization and the immutable startup state enforce when the bounded action may begin.

### Required observed recipe

- Exactly one nonrecursive writable repository bind; no automatic source creation, recursive submount, external hard link, extra owner mount, propagated mount or target path substitution. Host and mounted root device/inode must agree on the selected same-host mapping.
- Read-only image root. Enumerate all actual mounts and accept only the frozen versioned built-in proc/sys/dev/tmpfs/engine metadata mount recipe; distinguish these from owner resource mounts. Unexpected writable host-backed paths, image-declared volumes, Docker socket or devices deny. No assumption that `additional_mounts:false` removes Docker's system mounts.
- Nonzero expected UID/GID, exact identity mapping, no supplementary authority, all capability sets cleared, no-new-privileges, nonprivileged process, private PID/IPC/network/mount namespaces, no host namespaces and no exposed Docker socket. Rootless/userns-remapped/Docker Desktop configurations have no implicit equivalence; deny unless a separately proved mapping/backend supports them.
- Network `none`; no external connector. Inspect configuration, live namespace/interface observations and selected-target negative behavior must all agree. Do not claim all socket families are blocked merely from network mode.
- Seccomp enabled with the frozen selected runtime-default implementation/security recipe. Authenticate daemon/runtime implementation and security options, observe kernel mode and prove required negative syscall behavior in selected-target conformance. An unavailable, unconfined, substituted or version-unknown default denies; no fabricated filter digest is inferred from `Seccomp:2`.
- Exact enforced cgroup CPU, memory and PIDs ceilings matching the most restrictive composed/profile/action limits. Missing delegation, unsupported cgroup mapping, weaker limit or unknown observation denies. Wall clock/output bounds remain enforced by the host supervisor. No advisory-only limit counts as enforcement.
- Fixed manifest-checked image environment/entrypoint, no ambient host environment/credential/socket/shell, exact ImageID/manifest association and adapter executable. Keep image config, manifest and index identities distinct; do not replace PR #57's accepted ImageID meaning.

Read the actual cgroup v2 controller files for the adapter's live membership. `cpu.max` supplies quota/period bandwidth; require finite positive values, `cpu.max.burst = 0`, and the supported fair scheduler. Compare millicores with checked integer arithmetic: `quota * 1000 <= ceiling_millicores * period`; overflow denies. `memory.max`, not `memory.high`, supplies the memory hard limit; `pids.max` limits tasks, including threads. Require finite positive limits within the approved ceilings and the frozen swap policy. Kernel memory usage can temporarily exceed `memory.max`, and administrative task movement can exceed `pids.max`; claim controller enforcement, not an impossible instantaneous usage guarantee. Missing membership/controller association, malformed values, `max`, scheduler drift or ineffective mapping denies. Docker configuration, usage statistics and weights alone are insufficient. The source freeze must define bounded genuine cgroupfs reads and bind them to the private same-container kernel/daemon evidence.

## Interfaces and contracts

Private core inputs are validated HCFG-3 declaration, composed ceiling, stable loaded owner binding, selected-store custody, current authoritative install/generation/epoch and approved request. Platform observation is owned by the private backend, never supplied by the agent or deserialized into a permit. Separate `ResourceIdentityObservation` and `RuntimeControlObservation` from the unforgeable live startup guard. Future diagnostic output has fixed state/error codes and digests only; no authority conversion.

Before source integration, freeze the exact bounded startup frames, daemon API allowlist/version, native probe source/artifact recipe, host/kernel observation APIs, mount/cgroup/UID mapping formats, synchronization linearization, preparation journal and cleanup object selection. Bound every frame/read/metadata query by bytes, rows, depth, deadline and static error; reject unknown/duplicate/malformed required security fields, extra objects, stale nonce, wrong container and unsupported versions. Raw Docker output is untrusted until tied to the private current endpoint/container and validated; no generic JSON executor, subprocess command or arbitrary URL is exposed.

## States and failure handling

| State              | Meaning and permitted next step                                                                                                                          |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `unverified`       | Declaration/binding only. No initialization or action admission.                                                                                         |
| `prepared_inert`   | Current metadata and proved resource-free platform preparation; no target/action grant. Only accepted atomic bootstrap may bind it after fresh rechecks. |
| `attempt_claimed`  | One durable consumed attempt; no release yet. Interruption remains consumed/unknown until exact evidence resolves it.                                    |
| `startup_verified` | Private live same-attempt/channel guard after actual observation; one exact release after fresh store checks only.                                       |
| `released`         | Action may execute once. Receipt/reconciliation and cleanup remain required.                                                                             |
| `denied`           | No new grant/release. Do not weaken fields, skip a resource, select an older generation or choose another backend.                                       |
| `quarantined`      | Ambiguous preparation/container cleanup. No initialization/admission until separately authorized offline verified cleanup.                               |

## Data, privacy, and permissions

Bindings and host/runtime observations contain private paths, UIDs, mount/cgroup identities and endpoint metadata. Keep them owner-only and bounded; store only the exact required canonical binding/evidence digest in authority/audit records, with protected local details sufficient for recovery. Public routes, JSONL, logs/errors and `Debug` must not reveal raw source paths, environment, credentials, probe frames or resource bytes. No external source/report upload is required. Opaque declaration refs are claims until mapped by current owner evidence.

## Compatibility and migration

No current contract, parser, schema 17 migration, Phase 11 source lock, profile 1/2, public negotiation, CLI, route or running process changes in this design. Old/fake-runtime demonstrations remain experimental; they cannot be upgraded into HCFG-6 evidence. Activation of the new profile/protocol requires separately reviewed source integration with exact HCFG-5 generation/epoch/configuration binding. General historical-store/restore activation and automatic downgrade fallback remain closed. Phase 14 separately selects exact core-target rows and immutable artifacts after full headless/runtime/reliability gates.

## Non-goals and open questions

The human owner accepted the first capability tuple, privileged-component trust boundary, bootstrap metadata-observation amendment and handle order/lifetime, resource-free bootstrap probe and inert trusted-adapter startup barrier at the exact reviewed PR #72 head on 2026-10-01. [Docker Engine 29 release notes](https://docs.docker.com/engine/release-notes/29/) and [Engine API 1.56](https://docs.docker.com/reference/api/engine/version/v1.56/) establish the dated implementation/API recipe, not an installed host. The accepted private observation barrier and denial rules are LNSAT design conclusions; those sources do not prove a selected host or this implementation.
