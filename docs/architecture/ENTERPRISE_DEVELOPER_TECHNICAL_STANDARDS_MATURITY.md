# Enterprise Developer Technical Standards Maturity

> Hosted-service domain remains unselected and unreserved. Example hostnames in
> planning material are not valid operational endpoints.

## Purpose

This document strengthens enterprise and developer trust requirements with
named technical standards that enterprise buyers, security reviewers, platform
teams, and open-source contributors expect before trusting LNSAT as a full
open-source and commercial product.

This packet is source-only. It adds requirements and future feature obligations.
It does not execute audits, publish claims, create releases, change GitHub
settings, mutate Cloudflare, wire hosted runtime, process customer data, call
external services, or store secrets.

## Standards Maturity Model

LNSAT should expose standards in three states:

- `planned`: requirement accepted and visible in source/docs.
- `implemented`: feature exists with deterministic tests and source evidence.
- `verified`: evidence is generated by a repeatable pipeline or third-party
  process, with public status where appropriate.

Public pages may show planned standards, but must not imply certification,
compliance, downloadable artifact readiness, hosted-cloud readiness, or live
enterprise support until evidence exists.

## Standards To Add As Product Features

### Supply Chain And Release Integrity

Future features:

- SLSA-aligned provenance target with an initial SLSA Level 3 readiness path;
- in-toto provenance statement support for build and release attestations;
- CycloneDX and SPDX SBOM export support for every release family;
- Sigstore/cosign signing plan for containers and release artifacts;
- reproducible build recipes, pinned build environment refs, and builder
  identity evidence;
- OpenSSF Scorecard, OSV advisory scanning, dependency review, and license
  scanning as public release gates;
- signed commit/tag policy, branch protection requirements, and CODEOWNERS
  review paths before stable release;
- artifact transparency log refs, revocation list refs, and emergency disable
  refs on the download page.

### Security Engineering

Future features:

- NIST SSDF/SP 800-218-aligned secure development lifecycle map;
- OWASP ASVS and OWASP API Security Top 10 review checklist for Gateway,
  hosted APIs, and connector SDKs;
- STRIDE or equivalent threat-model workflow for Gateway, MCP adapters,
  modules, installers, clients, hosted cloud, and privileged helpers;
- CIS Benchmark posture notes for supported deployment modes;
- FIPS 140-3-friendly crypto inventory and enterprise crypto-mode notes;
- vulnerability disclosure SLA, coordinated advisory process, CVE path, and
  embargo process;
- security regression suite for policy bypass, approval bypass, audit bypass,
  capability escalation, tenant isolation, raw secret echo, SSRF, webhook
  spoofing, and package tampering.

### Identity, Access, And Tenant Boundaries

Future features:

- OAuth 2.1/OIDC profiles, PKCE, device flow boundaries, and service-account
  token rules;
- SAML 2.0 and SCIM 2.0 readiness for enterprise identity;
- WebAuthn/MFA policy hooks for administrative actions;
- RBAC/ABAC permission taxonomy with approval classes and break-glass policy;
- tenant, project, environment, and substrate isolation contracts;
- admin session hardening, audit session correlation, and least-privilege API
  token scopes.

### Audit, Observability, And Evidence Export

Future features:

- OpenTelemetry semantic-convention alignment for traces, metrics, logs, and
  audit evidence;
- CloudEvents or equivalent event envelope for policy/audit events;
- syslog RFC 5424 export posture, Elastic Common Schema mapping, and SIEM
  export contract;
- tamper-evident audit bundle format with hash chain refs and export manifest;
- evidence retention, legal hold, deletion, redaction, and audit export policy;
- status page, incident history, uptime/SLO evidence, and customer-facing
  maintenance notices before hosted-cloud launch.

### API, SDK, Module, And Developer Experience

Future features:

- OpenAPI specs for Gateway/public APIs and JSON Schema contracts for packet,
  module, release, and audit formats;
- MCP adapter compatibility profile and conformance suite;
- semantic versioning, API stability levels, deprecation windows, and migration
  guides;
- SDK compatibility matrix, golden fixtures, and conformance badges;
- docs versioning by release, changelog discipline, ADR/RFC process, and
  architecture decision traceability;
- module certification rules for permissions, telemetry, rollback, support
  state, license, dependency health, and provenance.
- portable instruction, skill, profile, context, graph, assignment, and
  model-overlay schemas with semantic compatibility and effective-bundle
  conformance;
- CLI/API/UI/MCP equivalence for proposals, assignments, approvals, receipts,
  and evidence without human-text parsing;
- extension lifecycle states for install, enable, grant, execute, quarantine,
  revoke, rollback, remove, and support.

### Reliability, Operations, And Enterprise Readiness

Future features:

- SLO/SLA vocabulary and uptime evidence model for commercial and hosted plans;
- backup/restore, disaster recovery, and HA runbooks with RPO/RTO targets;
- air-gapped install, offline mirror, and offline license/support path;
- upgrade, rollback, uninstall, and emergency disablement acceptance tests;
- support escalation, severity definitions, maintenance policy, and LTS policy;
- environment matrix for self-hosted, hybrid, SaaS, private cloud, and
  air-gapped deployments.

### Privacy, Data, And Commercial Trust

Future features:

- GDPR/CCPA readiness map, data inventory, data-flow map, data minimization,
  retention, deletion, and export controls;
- subprocessor inventory, DPA posture, region/data-residency plan, and customer
  data boundary docs before hosted cloud;
- no-phone-home default with explicit opt-in telemetry events and disablement;
- open-core versus commercial feature boundary, support entitlement mapping,
  and commercial maintenance rails;
- license compatibility, third-party notices, dependency license report, and
  module license review.
- enterprise policy for cross-project agent-content sharing, origin,
  classification, residency, retention, DLP, legal hold, export, and deletion;
- explicit entitlement-versus-authority separation and public-core security
  non-regression.

## Public Surface Requirements

Public pages should show these standards as planned features with clear status:

- `/security`: security engineering, identity, audit, compliance readiness, and
  blocked live claims;
- `/open-source`: developer standards, governance, release integrity,
  conformance, API stability, and community health;
- `/download`: supply-chain gates, artifact trust, provenance, SBOM, signing,
  revocation, and release-lane readiness;
- `/trust`: enterprise trust-center IA, compliance readiness, uptime/SLO,
  privacy, subprocessors, support, and hosted-cloud state;
- `/hosted`: hosted-cloud-only trust obligations, customer-data boundary, and
  `cloud.lnsat.com` not-live status.

## Standards Expansion

The maturity roadmap adds a second standards layer for procurement and developer
community trust:

- NIST AI RMF, ISO/IEC 42001 readiness, EU AI Act readiness, and model/tool/
  connector/module cards;
- CSA CCM/CAIQ, SIG, OSCAL, FedRAMP/StateRAMP posture, and trust-center
  evidence inventory;
- OPA/Rego policy packs, policy simulation/dry-run/diff/replay, SCIM
  entitlement sync, and separation-of-duties checks;
- VEX, EPSS, CVSS, CISA KEV, SSVC, security advisory, patch, backport, and LTS
  response policy;
- TUF-style metadata, signed release manifest verification, artifact quarantine,
  yanking, revocation, and reproducible-build diff reports;
- W3C Trace Context, data classification, DLP hooks, Splunk CIM, Elastic ECS,
  syslog, and JSON-lines export;
- OpenSSF Best Practices badge readiness, public API lifecycle states,
  conformance badges, contributor ladder, maintainer succession, and
  reproducible local development.

These remain planned/readiness-only until deterministic implementation evidence
and, where applicable, third-party verification exists.

## Acceptance Checks

- named standards are represented as backlog features, not claims;
- enterprise, developer-community, hosted-cloud, release, and governance
  standards stay separated;
- all public wording keeps planned/readiness-only status where evidence is not
  verified;
- fail-closed contracts reject missing standards, unsafe refs, live mutation
  flags, unexpected fields, and nonempty side effects;
- no DNS/Cloudflare, GitHub, release, hosted runtime, customer-data, audit,
  certification, package-build, signing, SBOM generation, or external service
  scope is opened.
