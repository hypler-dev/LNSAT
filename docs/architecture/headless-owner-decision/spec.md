# Specification: HCFG-5C exact owner decision for configuration widening

Status: proposed
Intent: [HCFG-5A protected transitions](../headless-protected-control/intent.md)
Authority: [Product Build Sequence, HCFG-5](../../PRODUCT_BUILD_SEQUENCE.md#headless-source-packet-order)
Owner: LNSAT maintainers
Accepted by: pending
Last updated: 2026-09-27

## Behavior

This is the separate owner security decision required by the proposed [HCFG-5A transition specification](../headless-protected-control/spec.md). It authorizes **one exact configuration widening or mixed transition**, never an action dispatch, resource access by itself, or a general policy override. A sole local owner may request and decide the change, but the decision step requires fresh current-credential proof and explicit confirmation of the exact canonical `comparison.v1` digest. A session, candidate, generic action approval, CLI flag, or agent request alone cannot decide. Existing distinct-requester/approver rules for consequential action approvals remain unchanged.

The trust claim is credential possession and an explicit recorded owner confirmation under the accepted local host-owner/credential-custody model. Neither `lnsatctl` terminal interaction nor Gateway can prove biological human presence. An automated client that obtains both the current owner credential and authenticated session is within a compromised owner trust boundary; the protocol must never label client-provided `human: true` or a terminal claim as proof. The owner must keep the credential out of agents. No alternate API, MCP, adapter, browser store, or direct SQLite path may create a configuration decision.

### Exact candidate and decision view

Gateway first persists an inert immutable candidate under the HCFG-5A owner-authenticated prepare operation. It reparses and composes the HCFG-3 declaration itself, verifies the selected installation and resource identities, computes the current effective envelope and policy/revocation floor, and derives the canonical `comparison.v1` snapshot and sorted change summary. `equal` and strict `narrowing` need no HCFG-5C decision; `unverifiable` denies. Only `widening_or_mixed` can request a challenge. Candidate bytes and client labels cannot choose that class.

Preparation and challenge creation each consume a durable limit of five attempts per 60 seconds per `(installation, owner)` across sessions; a restart does not reset either limit. At most four live inert candidates per `(installation, owner)` and two per owner session may exist across all candidate digests. Each declaration retains the HCFG-3 65,536-byte input limit; live candidate, comparison, and view storage together may use at most 1 MiB per `(installation, owner)`. Candidate lifetime is at most 15 minutes from preparation and cannot be renewed by replay. The Gateway expires and collects unreferenced candidates before quota evaluation in the same transaction and after restart; a candidate referenced by a live challenge or unused decision remains bounded by that reference's earlier expiry. A committed generation and immutable audit retain their own exact digests and evidence, never a permanent inert-candidate allocation. Quota exhaustion denies preparation or challenge creation without creating another row. Exact idempotent replay returns the same still-live record without consuming new quota; changed input under the key denies.

The owner decision view is an authenticated, closed projection bound to the candidate. It displays **every** changed resource identity, principal/action/capability tuple, access mode, approval obligation, and budget dimension needed to judge the increase, plus old/new generation and declaration digests and the full canonical comparison digest. Secret values and raw credentials never appear. If a change cannot be rendered completely within the bounded view, challenge creation denies; no ellipsis or partial summary can support consent. The visible view has a canonical digest stored with the challenge. A later view read must rederive the same digest, or deny and invalidate the challenge.

### Challenge and confirmation

The Gateway creates one cryptographically random, opaque, non-authorizing challenge ID for the exact candidate, current generation, owner identity/session, owner credential generation, installation and store instance, comparison snapshot/summary/view digests, policy/floor version, resource identity-evidence digest, stop/revocation epoch, and server-issued expiry. It persists at most one live challenge per `(installation, owner session, candidate, expected generation)`; an exact idempotency-key replay may return the same still-valid challenge, while changed input under that key denies. Challenge lifetime is at most ten minutes from trusted server time, including after restart. A challenge is never a bearer credential and cannot be moved to another session or candidate.

`lnsatctl` presents the complete protected view and requires an interactive owner to enter the **full displayed comparison digest** and current owner password through a masked controlling-terminal prompt. It offers no password argument, environment lookup, stdin channel, `--yes`, or auto-confirm option for widening; absent terminal denies before request. A later UI may use the same Gateway challenge/decision route with a protected credential field and explicit digest confirmation. The server never accepts a client assertion of terminal or human presence. The current owner password is carried only transiently in a bounded protected request to the existing numeric-loopback Gateway transport, with the active session bearer plus independent proof; it is zeroized after verification and excluded from URLs, logs, telemetry, traces, persistence, and response bodies.

Owner-decision credential verification uses the current Argon2id owner verifier **outside** the immediate SQLite write transaction. It consumes the existing known-owner identity limiter (currently five attempts per 60-second process window) and verified-session mutation limiter, and keeps a durable per-challenge failed-attempt count capped at three. A wrong password, digest mismatch, expired challenge, or exhausted limit returns one non-reflective denial; no decision is created. On a successful verification, the write transaction must re-read the same owner credential generation **and verifier identity**, so rotation between Argon2 work and commit denies. Every failed confirmation of a still-live challenge increments its durable counter in a serialized immediate transaction; the third failure closes it. That transaction checks the challenge is still live and bound to the same credential generation/verifier before incrementing, and never changes a consumed or invalidated challenge. If correct and incorrect attempts race, transaction order decides: a prior third failure denies the correct attempt, while a prior successful consume leaves later failures inert. Process-local limiter reset cannot revive a closed challenge.

### One-use decision and apply

One immediate transaction rechecks the live owner/session and independent proof, candidate, challenge, expiry, credential generation/verifier identity, full confirmed comparison digest, view digest, active generation, installation/store binding, resource identity, policy/floor, and stop/revocation epoch. It consumes the challenge once and appends a distinct immutable `configuration_owner_decision.v1` record and linked audit event atomically. The record binds owner identity and session reference, current credential generation/verifier reference digest, exact candidate and declaration digest, expected generation, comparison snapshot/summary/view digests, challenge ID/digest, issued/decided/expiry times, and outcome. It stores no password, PHC verifier, session token, CSRF proof, or raw resource details. A concurrent duplicate has one winner. A lost response is `unknown` until authenticated exact readback; no blind second decision.

The decision expires no later than five minutes after creation and no later than its challenge's original ten-minute deadline. It is a one-use reference, not a bearer grant. HCFG-5A apply requires a currently authenticated same owner/session and recomputes the complete comparison under one authoritative transaction. A changed generation, candidate, credential generation, verifier identity, session, resource identity, policy/floor, stop/revocation state, expiry, or view digest denies. On a successful apply, that same transaction consumes the decision, inserts the new immutable generation, advances the active pointer/epoch, and appends the configuration transition audit event. An exact idempotent replay returns the committed result without consuming again; a changed request denies. A failed apply rolls back decision consumption with all other source/audit writes, leaving it usable only while all original bindings and expiry still hold. An active stop never resumes through this decision.

## Interfaces and contracts

The proposed versioned Gateway operations are: owner-authenticated candidate prepare; owner-authenticated challenge create; authenticated exact challenge/view `GET|HEAD`; and owner-authenticated decision create. They share existing numeric-loopback Host/origin/fetch-metadata, product-surface selection, session bearer, independent proof, CSRF, closed body/field limits, same-origin, and generic-denial rules. The challenge and decision use separate owner-only permissions and record types; neither reuses `DecideApproval`, an action approval route, or a read-only evidence permission. Exact route spellings and wire schemas are frozen in a later accepted source packet, with no transport fallback or direct-store CLI bypass.

The challenge-create response exposes only an opaque ID, bounded expiry, complete protected view, and its canonical digests. The decision response exposes `recorded`, exact decision/event references and expiry, or a fixed denial. Authenticated exact readback distinguishes unused, consumed, expired, and unknown only to the bound owner session. `HEAD` repeats authentication and existence checks without a body. No public or agent-visible list/search/watch endpoint exposes pending decisions. Every response is redacted by a closed serializer, not a generic stored-row projection.

## States and failure handling

| State               | Meaning                                                                     | Allowed next action                                                         |
| ------------------- | --------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| `candidate_inert`   | Immutable prepared candidate; no owner decision                             | Exact owner challenge if comparison is widening/mixed.                      |
| `challenge_live`    | One bounded challenge/view bound to owner session and current evidence      | Current-credential and exact-digest confirmation only.                      |
| `challenge_closed`  | Expired, three failed attempts, consumed, or invalidated by evidence change | No decision; new candidate/challenge evaluation required.                   |
| `decision_unused`   | Durable one-use exact owner decision within its shorter expiry              | HCFG-5A apply after every current binding recheck.                          |
| `decision_consumed` | Committed apply references the decision                                     | Exact idempotent result readback only.                                      |
| `denied_or_unknown` | Failure, transport loss, or conflicting durable evidence                    | No authority inference; exact authenticated readback or a fresh evaluation. |

Credential rotation or recovery, owner disablement, session sign-out/revocation, active-generation change, stop/revocation change, policy/floor change, target identity change, or unreadable audit evidence makes pending challenges and decisions unusable even if their rows remain. Challenge/decision garbage collection must never erase the immutable decision/audit linkage needed to verify a committed transition. Authentication and rate-limit errors use the existing non-reflective denial posture; timeout never means non-execution. In-flight actions keep their receipt/reconciliation obligations.

## Data, privacy, and permissions

Only Gateway verifies the password and commits challenge/decision state. The host-owner and current credential are the V1 authority root; no client-provided human flag, signed text, generic approval, agent role, or UI state substitutes for server verification. Protected store rows contain bounded references and digests; sensitive view content remains available only to the owner session and is never logged. Raw password and verifier bytes are held only transiently for Argon2id verification and zeroized. Failure counters and rate-limit effects are security state, not proof of an owner decision.

## Compatibility and migration

This proposal changes no current route, schema, CLI, or action-approval behavior. Existing schema-17 stores have no configuration candidate/challenge/decision table and no active headless generation. A future migration initializes all new authority records empty and inactive. HCFG-3 diagnostic output, `config diff`, and an old action approval cannot be imported as a decision. A source downgrade that cannot verify the decision/generation/audit schema denies activation. HCFG-5B bootstrap, HCFG-6 selected-platform enforcement, and a separately accepted HCFG-5A apply contract remain prerequisites.

## Non-goals and open questions
